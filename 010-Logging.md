
# 📘 MuleSoft Logging

This document provides a minimal, practical overview of logging in Uprizon Mule applications.
It explains the two log types used in the Starter App and Common Modules: Root Log and Observability Log.    

📌 NB: To make my document easier to read, the example application is named sf-case-api-impl. Therefore, whenever we reference a file location in our examples, we will use this Mule application as the reference.

### Root Log Principles
* Shows Mule engine activity
* Mirrors console output
* Used for debugging runtime behavior
* Not intended for business observability

**Example** :
```
INFO  Message source 'listener' on flow 'sf-case-api-main' successfully started
WARN  Unknown channel option 'SO_TIMEOUT'
```

### Observability Log Principles
* Provides end‑to‑end visibility of API execution
* Captures business‑level tracepoints
* Ensures correlation across flows and systems
* Designed for monitoring platforms

**Example** :
```
{"tracePoint":"START","flowName":"get:\\cases\\(caseId):sf-case-api-config","message":"Flow started"}
{"tracePoint":"BEFORE_API","message":"Salesforce SOQL query Case"}
{"tracePoint":"AFTER_API","elapsedMs":3987,"message":"Salesforce SOQL query Case"}
{"tracePoint":"END","elapsedMs":4094,"message":"Flow completed"}
```


## 2. Logging Configuration Keys
### Root Log (Text Log)   

**Purpose**:      
System-level and runtime logs generated by Mule Runtime Engine.

**Contains**:    
* Flow startup/shutdown
* HTTP Listener / HTTP Request internal logs
*Connector logs (Salesforce, HTTP, APIKit)
* Runtime warnings (Jetty, Reactor Netty)
* Exceptions not captured by Observability

**Format**:      
Human‑readable text (PatternLayout).

**Configured** in log4j2.xml:
```
<AsyncRoot level="INFO"> <AppenderRef ref="file"/> </AsyncRoot>
```

### Observability Log (JSON Log)

**Purpose**:      
Structured JSON logs for business observability and monitoring.

**Contains**:    
* TracePoints (START, END, BEFORE_API, AFTER_API, BEFORE_TRANSFORM, AFTER_TRANSFORM, EXCEPTION)
* Correlation IDs
* Root Correlation IDs
* Execution time (elapsedMs)
* Payload size
* Optional JVM metrics (e.g., heapUsedPercent)
* Business messages

**Format**:      
One JSON object per line.    
No decoration.    
Ready for Splunk / ELK / Datadog ingestion.    

**Configured** in log4j2.xml:
```
<AsyncLogger name="uprizon.observability" level="INFO" additivity="false">
    <AppenderRef ref="observabilityJson"/>
</AsyncLogger>
```

**Key rule**:  
additivity="false" ensures JSON logs never mix with root logs (no duplicate).    

👉 Where we find the logs     
| Type de log                | Local                                        | CloudHub 2             |
|----------------------------|----------------------------------------------|------------------------|
| **Root Log**               | logs/sf-case-api-impl.log                    | Runtime Manager → Logs |
| **Observability JSON Log** | logs/sf-case-api-impl-observability.json.log | Anypoint Monitoring → Log Search (category uprizon.observability) |


## 3. Summary
* **Root Log** → runtime, connectors, warnings, startup
* **Observability Log** → structured JSON, tracepoints, correlation IDs, metrics
* Logs are **intentionally separated** 
* Observability logs are **never printed to console**
* This structure is standardized in the **Starter App** and **Common Modules**
